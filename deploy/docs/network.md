# Laptop <-> Go2 network

The laptop and the robot talk over one Ethernet cable, never over WiFi. If the robot learns a
second (WiFi) address of the laptop it may stream `/lowstate` there, with 20-250 ms gaps, which
the 100 Hz controller cannot tolerate.

## Addresses

| Setting (config/deploy.env) | What |
|---|---|
| `DEMO_ROBOT_IP` | the Go2's Ethernet address (see Unitree's documentation for the robot's subnet) |
| `DEMO_LAPTOP_IP` | a free static address for the laptop's wired interface in the same /24, no gateway, no DNS |
| `DEMO_NIC` | the laptop's wired interface (`ip -br link`) |
| `X5_IP` | the RDK X5 camera host on the same /24 (camera tools in `scripts/x5/`) |

The robot scripts configure `DEMO_LAPTOP_IP/24` on `DEMO_NIC` themselves when it is missing (this
needs `sudo`); to do it by hand:

```bash
sudo ip addr flush dev $DEMO_NIC
sudo ip addr add $DEMO_LAPTOP_IP/24 dev $DEMO_NIC
sudo ip link set $DEMO_NIC up
```

A NetworkManager connection with the same static address makes it permanent.

## Checks

```bash
ip -br addr show dev $DEMO_NIC          # UP, $DEMO_LAPTOP_IP/24
ip route get $DEMO_ROBOT_IP             # ... dev $DEMO_NIC src $DEMO_LAPTOP_IP
ping -c 3 $DEMO_ROBOT_IP
```

The robot scripts run these checks before every run, then verify that the 500 Hz `/lowstate`
stream (~0.65 MB/s) really arrives on `DEMO_NIC` and on no other interface, and the controller
refuses to stand up while it does not (parameter `wired_nic`).

## DDS binding

The ROS 2 processes are bound to the wired interface:

- FastDDS (default): a participant profile whose interface whitelist is the laptop's wired
  address. The scripts generate it from `DEMO_LAPTOP_IP`; `config/fastdds_wired.xml` is the same
  profile for manual use (replace `@LAPTOP_IP@`), `config/fastdds_wired_shm.xml` adds host-local
  shared memory for the large camera images exchanged between local processes.
- CycloneDDS: `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp` with a `CYCLONEDDS_URI` naming `DEMO_NIC`
  (generated by the scripts; `sudo apt install ros-jazzy-rmw-cyclonedds-cpp`).

The same profiles put `ros_discovery_info` (the node-name topic) in its own partition
`wam_jazzy_graph`: a ROS 2 Humble node on the network (the RDK X5 camera host) cannot parse
Jazzy's node-name messages. Data topics are not affected. Use these profiles for every ROS
process on the laptop, and not on the X5.

After binding, restart the ROS 2 CLI daemon once (`ros2 daemon stop`): a daemon started without
the binding cannot see the bound nodes.

## Topics

ROS 2 names `/lowstate` and `/lowcmd` are the DDS topics `rt/lowstate` and `rt/lowcmd` of the
Unitree SDK2.

| Topic | Direction | Use |
|---|---|---|
| `/lowstate` | robot -> laptop, 500 Hz | joints (q, dq, tau_est), IMU, fault bits |
| `/lowcmd` | laptop -> robot, 100 Hz | q, dq, tau, kp, kd per joint (with Unitree's CRC) |

This deployment reads no foot contact force: foot contacts come from the gait schedule.

## Low-level control

Unitree's built-in motion service must release the motors before any LowCmd is sent:
`CheckMode()` must return an empty name (a name such as `mcf` means the service still overrides
`/lowcmd`). `ros2 run wam_go2_deploy release_sport_mode` loops CheckMode / ReleaseMode until the
name is empty and exits 0; any other exit code means do not continue. The robot scripts run it
for you.

Before anything publishes `/lowcmd`:

- no other LowCmd publisher is running (`pgrep -fa go2_low_level`, no second controller);
- the route and the ping above work;
- for a first test, the robot hangs in a frame with its feet off the ground and someone stands
  next to it.

The controller starts in DAMP. Requests on `rambo/fsm_cmd` (`std_msgs/String`) move it:
`STAND`, `POLICY`, `DAMP` (any time), `REARM` (after a safety trip, once the cause is gone).
Stopping the node (Ctrl+C) sends damping frames before it exits.
